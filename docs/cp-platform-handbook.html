Part I

The idea

What the platform is, what it feels like to use, and the vocabulary the rest of the handbook relies on.

Everyone

1What this project is

CP Platform is a website where people practise programming by solving puzzles, and where a computer checks their answers automatically. "CP" stands for competitive programming, the sport behind sites such as Codeforces, LeetCode and HackerRank.

A puzzle (called a problem) looks like this: "You are given two numbers. Print their sum." The person solving it does not type the answer. They write a small program that can compute the answer for any pair of numbers, and submit that program to the website.

The website then acts as an examiner. It holds a set of secret test questions for the problem, for example "3 and 4 → 7", "−10 and 10 → 0", "1,000,000 and 1 → 1,000,001". It runs the submitted program on each question, compares what the program printed with the correct answer, and gives a verdict: ACCEPTED if every answer was right, or a specific failure such as WRONG_ANSWER or TIME_LIMIT_EXCEEDED.

The difficult part: running strangers' code safely

Running a program written by an unknown person on your own server is dangerous. The program could delete files, read secrets, attack other computers over the network, or simply loop forever and use up the machine. An online judge must run that code anyway, thousands of times a day.

This project solves that the same way a laboratory handles a dangerous sample: inside a sealed box. Each run happens inside a Docker container, a lightweight isolated environment with no network connection, a fixed amount of memory, a cap on how many processes it may start, a file system it cannot modify (apart from one scratch folder), and a stopwatch. When the run ends, the box is thrown away. Chapter 22 examines each of those walls in detail.

What it is made of, in one paragraph

The part you see in the browser (the frontend) is a React web application. It talks to a backend server written in Java with the Spring Boot framework. The backend stores users, problems and results in a PostgreSQL database, and when a program needs judging it asks Docker to start a sealed container for it. Everything can be started with a single command using Docker Compose.

What it is not (yet)

  • It is not a contest system: there are no timed rounds, no penalties, no per-contest rankings.
  • It is a single server. One backend process does everything, including judging. Chapter 30 describes how it would be split up to handle more users.
  • It has no automated test suite. There is no src/test folder in the backend.

2A tour from the user's chair

This chapter walks through the site the way a visitor experiences it. Later chapters explain what happens behind each click.

A visitor who is not logged in

The home page lists problems in a table: title, a coloured difficulty badge (Easy, Medium, Hard) and tags such as "arrays" or "math". A dropdown filters by difficulty. The Leaderboard link shows users ranked by how many different problems they have solved. Clicking a problem opens its page: the statement, any constraints, and a few sample tests (example inputs with their correct outputs) so the solver can see the expected format. Below that sits a code editor, the same editor that powers Visual Studio Code, with a language selector for C++, Python and Java.

A visitor can read everything and even type code, but pressing Submit sends them to the login page.

Registering and logging in

The Register page asks for an email, a username (3 to 30 characters) and a password (at least 8 characters). After registering, the visitor is logged in immediately and their username appears in the top bar with a Logout button. Logging in later uses email and password.

Solving a problem

  1. The user picks a language. The editor fills with a starter template, for example a C++ main function.
  2. They write a solution that reads the input from standard input (the keyboard, as far as the program knows) and prints the answer.
  3. They press Submit. The page immediately moves to a submission page with a grey PENDING badge.
  4. Every 1.5 seconds the page asks the server for news. After a few seconds the badge turns into the verdict. A score shows what percentage of the tests passed, the runtime of the slowest test is shown, and a table lists each test as "Sample n" or "Hidden n" with its own verdict.
  5. If the code failed to compile, the compiler's error message is shown so the user can fix it.

Solving a problem for the first time adds one to the user's solved count, which moves them up the leaderboard.

The administrator's view

Users with the ADMIN role see extra controls. A "+ New Problem" link in the top bar opens a form for title, difficulty, statement, constraints, time limit, memory limit, tags and any number of test cases, each with input, expected output and a "Public (sample)" checkbox. On a problem's page, admins also see Edit and Delete buttons.

There is no screen for making someone an admin. The first administrator is created by changing their role directly in the database (chapter 25 shows the command).

Why the backend runs Docker from inside Docker

The backend itself runs in a container, yet it has to start other containers. Rather than run a full Docker engine inside the backend container ("Docker-in-Docker"), the project mounts the host's Docker control socket, /var/run/docker.sock, into the backend. The backend container only has the Docker client; every docker run it issues is executed by the host's daemon. The new runner containers are therefore siblings of the backend, not children. This pattern is sometimes called "Docker-out-of-Docker". It is simple and fast, and it has a serious security cost covered in chapter 22.

It also creates a path puzzle. The backend writes each submission's source code to a folder, then asks the daemon to mount that folder into a runner container. The daemon interprets the path on the host, not inside the backend container. That is why docker-compose.yml mounts /tmp/judge-workspace at the identical path on both sides: the folder the backend writes into and the folder the daemon mounts are the same physical directory. If the two paths differed, the daemon would mount an empty folder and every submission would fail to compile.

7Inside the backend

The backend follows the conventional Spring layering. Each layer only calls the one below it, with one exception noted at the end.

flowchart TB
  F["Security filters: JwtAuthFilter, URL rules"] --> C["Controllers: parse HTTP, validate, pick principal"]
  C --> S["Services: business rules, transactions"]
  S --> R["Repositories: Spring Data interfaces"]
  R --> E["Entities: JPA classes"]
  E --> DB[("PostgreSQL")]
  S --> J["JudgeService: Docker processes"]
  C -.-> D["DTO records: request and response shapes"]
  S -.-> D
  X["GlobalExceptionHandler"] -.->|"catches exceptions from controllers and services"| C

Figure 7.1 · Backend layers.

Controllers

Controllers are deliberately thin. They declare the URL, read path variables and query parameters, trigger validation with @Valid, receive the logged-in user via @AuthenticationPrincipal User, call one service method and wrap the result in ResponseEntity.ok(...). The principal is the actual User entity, because JwtAuthFilter places the entity itself into the security context (chapter 13).

Services

All decisions live here: does this email already exist, what is the slug, may this user see this submission, which verdict does this run deserve. Methods that touch several rows are annotated @Transactional so they succeed or fail as a whole. ProblemService.create, update, delete, getBySlug, getForAdmin and JudgeService.judgeAsync are transactional; the rest rely on the per-call transactions of repository methods.

Repositories

Seven interfaces extend JpaRepository. Spring Data generates their implementations at startup by parsing method names. For example findByProblemIdAndIsPublicTrue(Long problemId) becomes "select test cases whose problem id equals ? and whose isPublic is true". Only one query is hand-written: TestCaseRepository.deleteByProblemId, a bulk JPQL delete marked @Modifying.

Entities

Seven classes map to tables (chapter 8). All use Lombok's @Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder; fields with default values use @Builder.Default so the builder respects them. Timestamps are filled by @PrePersist callbacks. Relationships to other entities are LAZY: the related row is loaded only when first accessed.

DTOs

Requests and responses are Java records, grouped as nested types inside holder classes (AuthDtos.RegisterRequest, ProblemDtos.ProblemDetail, and so on). Entities are never returned directly. This is what keeps hidden test cases and password hashes out of responses: a DTO can only expose the fields it declares.

Cross-cutting pieces

  • ApiException carries a message and an HTTP status. Services throw it for expected failures (not found, conflict, forbidden).
  • GlobalExceptionHandler turns ApiException into {"error": message} with its status, validation failures into a 400 with one entry per field, and any other exception into a 500 with "Internal server error: " + message. That last rule matters for several cases in Part IV.

The one layering exception

ProblemController.delete calls SubmissionRepository.countByProblemId directly and passes the count into the service. It works, but the check belongs inside ProblemService.delete.

Table notes

TableImportant details

How rows come into existence

  • Register inserts one users row.
  • Create problem inserts one problems row, any new tags, the problem_tags links and one test_cases row per test.
  • Submit inserts one submissions row (status PENDING).
  • Judging updates that submission, inserts one submission_results row per test, and inserts or updates one user_progress row.

Authentication state

AuthContext keeps one object, user = {id, username, role}, and exposes login, register and logout. On page load it restores user from localStorage. After a successful login or register it stores three keys: accessToken, refreshToken and user. Logout calls localStorage.clear() and sets user to null; nothing is sent to the server.

RequireAuth redirects to /login if there is no user. RequireAdmin redirects to / unless user.role === 'ADMIN'. These guards are about user experience only. The real enforcement is on the server; anyone can edit localStorage to claim to be an admin, and the server will still refuse their admin calls.

The API client

api/client.js creates an Axios instance with base URL /api and two interceptors:

  • Request interceptor: reads accessToken from localStorage and adds the Authorization header.
  • Response interceptor: if a response is 401 and the request has not been retried, it posts the refresh token to /api/auth/refresh (with plain Axios so the interceptor does not loop), stores the new pair, and replays the original request. If refreshing fails, it clears storage and does a full-page redirect to /login.

The relative base URL is what makes the same build work in development and production. In development, Vite's dev server proxies /api to localhost:8080. In production, nginx proxies /api/ to backend:8080.

Stage by stage

  1. nginx (production) or the Vite proxy (development) forwards the request to the backend.
  2. Tomcat assigns a worker thread. Everything up to the response happens on that thread.
  3. CORS filter. Only relevant when the page comes from a different origin. Allowed origins are http://localhost:*. Under compose the browser talks to one origin, so CORS never applies.

  5. Authorization. URL rules are checked in order; the first match wins. If the rule needs an authenticated user and there is none, the entry point returns 401. If the user lacks the role, the access-denied handler returns 403.
  6. DispatcherServlet finds the controller method, converts JSON to the request record and runs bean validation if @Valid is present.
  7. Method security. @PreAuthorize("hasRole('ADMIN')") on getForAdmin and delete is evaluated before the method runs (a second check on top of the URL rule).
  8. Controller → service → repository. Business logic runs; transactional methods open a database transaction.
  9. Serialization. Jackson writes the returned record as JSON.
  10. Errors. Exceptions thrown from a controller or service go to GlobalExceptionHandler. Exceptions inside the security filters never reach it; they are handled by the entry point and access-denied handler.

13.3 What is inside the tokens

Both tokens are JWTs signed with HMAC using the jwt.secret setting. JJWT chooses the strongest HMAC variant the key length allows; the shipped secrets are 57 and 62 bytes long, which selects HS384. A decoded access token payload looks like this:

{
  "sub": "ada@example.com",   // identity: the email
  "role": "USER",
  "userId": 7,
  "type": "access",           // "refresh" in a refresh token
  "iat": 1791540902,          // issued at (seconds)
  "exp": 1791541802           // +15 min; refresh tokens: +7 days
}

The refresh token contains only sub, type, iat and exp. The role and userId claims in the access token are never read by the backend; the filter always loads the user from the database. That means a role change takes effect on the user's very next request, at the cost of one database query per authenticated request.

Tokens are signed, not encrypted. Anyone holding one can read its contents; they just cannot change them without breaking the signature.

13.4 An authenticated request

Covered step by step in chapter 12. In short: header → signature and expiry check → type must be "access" → user loaded by email → principal set → URL rule check → controller receives the User entity through @AuthenticationPrincipal.

On the server, AuthService.refresh checks the token's type is "refresh", finds the user, and issues a brand-new pair. An expired refresh token throws inside JJWT before the expiry check in the service is reached, so the response is a 500 rather than the intended 401. The client treats any failure the same way, so the user experience is unaffected.

The old refresh token is not invalidated when a new one is issued. Every refresh token stays valid for its full 7 days.

13.6 Logging out

Logout is purely client-side: localStorage.clear() and user = null. The server keeps no session and has no token blacklist, so a copied token keeps working until it expires: up to 15 minutes for an access token and up to 7 days for a refresh token.

14.5 Deleting a problem

The controller counts submissions for the problem. If there are any, the service throws 409 with an explanatory message. Otherwise it bulk-deletes the test cases, then deletes the problem; Hibernate removes the problem_tags links. Tag rows themselves remain.

15.6 The compile step

For C++ and Java, one container runs the compile command with a fixed 20-second timeout. If the exit code is not 0 (including a timeout, which is reported as exit code −1), the submission becomes COMPILE_ERROR, the first 4,000 characters of the compiler's error output are saved as errorMessage, judgedAt is set, and the method returns. No test results are written and user_progress is not touched, so compile errors do not count as attempts. The compiled sol or Main.class stays in the workspace for the test runs.

15.7 Running each test

The test cases are loaded with findByProblemId (hidden and public together, in database order, normally by id). For each one:

  1. The test's input is written to input.txt, overwriting the previous one.
  2. The timeout is computed as ceil(max(1, timeLimitMs / 1000)) + 2 seconds.
  3. The run command executes in a fresh container with the input piped in.
  4. The verdict is decided (figure 15.3).
  5. A submission_results row is saved with the verdict and wall-clock time.
  6. If this is the first non-accepted test, its verdict becomes the overall verdict.

All tests run even after a failure. That gives a complete per-test table and an accurate score, at the cost of judging time, which matters most when every test times out (case A4).

15.9 Finishing up

  1. Score = round(100 × passed ÷ total). Two of three tests passing gives 67. Test weights are ignored.
  2. The submission gets its final status, score, the maximum runtime across tests, and judgedAt.
  3. updateProgress finds or creates the user's user_progress row for this problem, adds one to attempts, and, if the verdict is ACCEPTED and the problem was not solved before, sets solved = true and records this submission's id.
  4. The transaction commits. At this instant the verdict, every result row and the progress update become visible together.
  5. The finally block deletes the workspace folder, whatever happened.

If any exception escapes during judging (for example the docker program does not exist), the catch block marks the submission INTERNAL_ERROR with the exception message and saves it.

Only compile errors and internal errors carry a message; a program's own error output (for example a Python traceback) is written to the server log and never shown to the user.

WRONG_ANSWER, 67%, with "Hidden 2" in red. They do not see the hidden input or their output for it; that is deliberate.

Situation

A4
An infinite loop
TIME_LIMIT_EXCEEDED
Situation

while (true) {} on a problem with 10 tests and the default 2,000 ms limit.

What happens

Each test waits the full 4-second timeout, then the judge kills the local docker client process and records TLE. All 10 tests do this, so judging takes about 40 seconds. Killing the client does not stop the container: the daemon keeps it running, and since the loop never ends, --rm never fires. Ten containers are left spinning, each using up to a full CPU core, until someone runs docker kill or restarts Docker.

User sees

TIME_LIMIT_EXCEEDED after roughly 40 seconds of PENDING. Over time, every user sees slower judging and eventually spurious TLEs as leaked containers pile up. This is the most serious known issue (chapter 29).

A5
A crash

Situation

The run finishes in time with a non-zero exit code: RUNTIME_ERROR. The judge logs the exit code and the first 500 characters of standard error at WARN level on the server.

User sees

RUNTIME_ERROR with no explanation. The traceback is in the server log only. Hiding it prevents a solver from printing hidden test data through error messages, but also makes debugging harder.

A6
Using too much memory
RUNTIME_ERROR
Situation

What happens

The container's 256 MB cap is hit. All of these are non-zero exits: RUNTIME_ERROR. The problem's own memoryLimitMb is never used, so a problem set to 64 MB or 1,024 MB is still judged at 256 MB.

User sees

RUNTIME_ERROR, never MEMORY_LIMIT_EXCEEDED.

The judge waits for the process to finish before reading its output. Operating-system pipes hold roughly 64 KB; once full, the program blocks waiting for someone to read, and nobody does. User sees

TIME_LIMIT_EXCEEDED on a correct solution. Problems with large outputs cannot currently be judged.

21.1 What is being protected, and from whom

21.2 Stateless authentication

The server keeps no sessions (SessionCreationPolicy.STATELESS). Every request proves its identity with an access token, and the server can verify that token using only the secret key. The benefits are simplicity and horizontal scaling: any number of backend instances can verify any token. The costs are revocation (a token cannot be cancelled before it expires) and the need for a refresh mechanism so short access lifetimes do not force constant logins. This project accepts both costs and does not add a blacklist.

21.3 Why anonymous authentication is disabled

Spring Security normally gives unauthenticated requests an "anonymous" identity. Access to a protected URL by an anonymous identity is treated as access denied and, combined with a custom access-denied handler, would come back as 403. The frontend only refreshes tokens on 401. Disabling anonymous authentication (.anonymous(anon -> anon.disable())) makes a missing or expired token produce "no authentication at all", which goes to the entry point and yields a 401. Public URLs still work because permitAll() grants access without ever looking at the authentication. The comment in SecurityConfig documents this reasoning.

21.4 Two layers of authorization

Admin endpoints are protected by URL rules in SecurityConfig. Two of them (getForAdmin and delete) are additionally annotated with @PreAuthorize. create and update rely on the URL rule alone. That is sufficient today, but if someone later moves or renames those routes, the URL rule could stop matching and the endpoints would silently become available to every logged-in user. Adding @PreAuthorize to all four admin methods would make protection independent of the URL layout.

21.5 Token storage in the browser

Tokens live in localStorage, readable by any JavaScript on the page. If an attacker could inject script (cross-site scripting), they could steal the tokens. The current UI resists that: React escapes all text it renders, problem statements are displayed as plain text (white-space: pre-wrap), and there is no dangerouslySetInnerHTML anywhere. If problem statements are ever rendered as Markdown or HTML, they must be sanitized, or the tokens should move to HttpOnly cookies.

CSRF protection is disabled. That is correct for this design: CSRF attacks rely on the browser attaching credentials automatically (cookies), and this API only accepts credentials from an explicit Authorization header.

21.6 Hidden tests and side channels

Hidden test content never appears in a non-admin response, the sandbox has no network, a program's error output is not returned, and each workspace contains only that submission's files (the expected output is never written to disk). A determined cheater can still learn about hidden tests through side channels that every online judge shares: per-test verdicts, deliberate crashes or timeouts that depend on the input, and runtime differences. Defending against that is outside the scope of a project like this.

21.7 Information in error messages

The catch-all handler returns "Internal server error: " + ex.getMessage(). For database errors that message can include SQL fragments and constraint names; for type errors, Java class names. It helps during development and gives an attacker a map of the internals in production. A production build should log the detail and return a generic message.

21.8 Secrets and exposed ports

  • JWT_SECRET is hard-coded in docker-compose.yml, and a fallback secret sits in application.yml. Anyone who knows the secret can mint an admin token for any email.
  • The database password is cpplatform.
  • Compose publishes Postgres on port 5432 and Redis (no password) on 6379 to all interfaces. On a cloud VM without a firewall, both are reachable from the internet.

All three are fine on a laptop and must change before any public deployment (chapter 28).

21.9 The Docker socket

Mounting /var/run/docker.sock into the backend gives the backend full control of the host's Docker engine. Anyone who can run commands as the backend can start a privileged container that mounts the host's root file system, which amounts to root on the host. Submitted code never gets the socket (runner containers do not mount it), so the risk is a vulnerability in the backend itself, not in the sandbox. The README states this trade-off. The standard mitigation is to move judging to a separate machine or VM that holds nothing else of value.

22The sandbox, flag by flag

A container is not a virtual machine. It is a normal Linux process that the kernel places inside namespaces (its own view of processes, network, mounts and users) and control groups (resource limits). All containers share the host kernel. The question for a judge is which walls exist and which are missing.

22.1 The container leak, precisely

On timeout the judge calls process.destroyForcibly() on the docker run client process. The client is only a messenger; the container belongs to the daemon. Killing the messenger does not stop the container, and --rm only removes a container after it exits. A robust version names each container (--name judge-31-4) and runs docker kill judge-31-4 on timeout, or wraps the command in the timeout utility inside the container so the process ends itself (the class comment mentions a timeout backstop, but it is not implemented). Docker's --stop-timeout does not help, because nothing ever asks the container to stop.

22.2 The output deadlock, precisely

process.waitFor(timeout) is called before anything reads process.getInputStream(). The child writes into a pipe of fixed capacity; when it is full, the child's write call blocks; the child can then never exit, so waitFor times out. The fix is to drain standard output and standard error concurrently, on separate threads or with ProcessBuilder.redirectOutput to files, and to cap the amount read so a program cannot exhaust the judge's memory.

22.3 What "time" means here

The measured time is wall-clock time of the docker run client, including image lookup, namespace creation, cgroup setup, process start, the program itself, and container removal. On a typical machine the overhead alone is 300–900 ms, varies with load, and is the same for a C++ solution and a Python one. Proper judges measure CPU time of the user process from inside the sandbox (for example from the cgroup's cpu.stat, or with /usr/bin/time), and keep containers warm instead of creating one per test.

22.4 Stronger isolation options

  • gVisor (--runtime=runsc): intercepts system calls in a user-space kernel, so a kernel exploit has to break gVisor first. Drop-in for this design.
  • Firecracker microVMs: real virtual machines that start in about 125 ms. Strongest isolation; more infrastructure.
  • isolate (the sandbox used by the International Olympiad in Informatics): lightweight, measures CPU time and memory precisely, designed for judges.
  • Cheap hardening of the current setup: --cap-drop=ALL, --security-opt=no-new-privileges, --ulimit fsize=... to cap file size, and a size-limited tmpfs for /box with the files copied in.

23.1 Who runs what

23.2 Why submit() must not be transactional

submit() saves the submission and then queues the judge. Because submit() has no surrounding transaction, the save commits before the queueing call. If someone later adds @Transactional to submit(), the commit would move to the end of the method, after judgeAsync was queued. The worker thread could then run findById before the commit, find nothing, and throw from orElseThrow(). The submission would stay PENDING forever, intermittently, depending on timing. The robust pattern is to trigger judging after commit, for example with @TransactionalEventListener(phase = AFTER_COMMIT), or to use a queue (chapter 30).

23.3 One long transaction in the judge

judgeAsync is both @Async and @Transactional. The async proxy moves the call to a worker thread; the transactional proxy opens a transaction on that thread that lasts until judging ends. Consequences:

  • RUNNING is never visible. Under Postgres's default read-committed isolation, pollers only see committed data.
  • Results appear all at once. Partial results cannot be shown while judging is in progress.
  • A connection is held for the whole judging time, up to tens of seconds (case A16).
  • Error handling can fail. If a database exception occurs inside the loop (say a constraint violation saving a result), Spring marks the transaction rollback-only. The catch block then sets INTERNAL_ERROR and saves, but the commit throws UnexpectedRollbackException, everything rolls back, and the submission remains PENDING.

A better shape is short transactions: one to mark RUNNING, one per result (or one at the end), one to finish. The Docker work itself needs no transaction at all.

23.4 How @Async works here

@EnableAsync makes Spring wrap beans that have @Async methods in a proxy. A call from another bean goes through the proxy and is submitted to the executor; the caller gets control back immediately. Two rules follow. A call from inside JudgeService to its own judgeAsync would bypass the proxy and run synchronously. And because the method returns void, any exception that escapes it is only logged by Spring's default uncaught-exception handler; the caller never learns about it.

23.5 Lazy loading and "open session in view"

Relationships are lazy, so for example problem.getTags() issues a query when first called. That only works while a Hibernate session is open. Spring Boot enables spring.jpa.open-in-view by default, which keeps a session open for the whole web request, and logs a warning about it at start-up. This is why ProblemService.list (not transactional) can map tags, and why SubmissionService.toView can read result.getTestCase().isPublic(). Inside judgeAsync there is no web request; the method's own transaction provides the session.

The User principal is loaded inside the security filter, before the open-session interceptor starts, so it arrives in controllers as a detached entity. Using it as a reference when saving a new submission is fine, because only its id is needed for the foreign key.

24Spring subtleties

24.1 The JWT filter is registered twice

JwtAuthFilter is a @Component that implements Filter. Spring Boot automatically registers every filter bean with the servlet container, and SecurityConfig adds it to the security chain. It therefore sits in two chains. It still runs only once per request because it extends OncePerRequestFilter, which marks the request after the first pass. The usual way to make this explicit is a FilterRegistrationBean with setEnabled(false).

24.3 The -parameters compiler flag

@PathVariable Long id and the JPQL parameter :problemId in TestCaseRepository are bound by matching Java parameter names. Those names only exist at runtime if the code is compiled with -parameters. The Spring Boot parent POM enables it, so Maven builds work. Building with a tool that does not set it fails at runtime with "name for argument ... not specified". Explicit names (@PathVariable("id"), @Param("problemId")) remove the dependency.

24.4 Lombok and booleans named isX

For the field boolean isPublic, Lombok generates the getter isPublic() and the setter setPublic(), while the builder method is isPublic(...). The code uses the getter and builder only, so this is consistent. The JSON property in the DTO records is isPublic; with Jackson 2.17 records serialize and deserialize with that exact name (tested).

24.5 Schema management

ddl-auto: update adds tables and columns but never removes, renames or retypes them, and it does not run data migrations. Hibernate 6 also generates check constraints for enum columns; adding a new value to an enum such as Language later may not update the existing constraint, and inserts with the new value would then fail. A real deployment should switch to Flyway or Liquibase migrations and set ddl-auto: validate.

24.6 Smaller details

  • Returning a Page directly from a controller works but Spring Data 3.3 logs a warning that the JSON structure is not guaranteed to stay stable.
  • The Redis starter is on the classpath and configured; it is unused.
  • judge.default-time-limit-seconds is defined in application.yml and read nowhere.
  • ProblemService.getEntityById carries a comment saying it is package-private; it is public.
  • The DaoAuthenticationProvider bean is picked up by AuthenticationConfiguration, which is how AuthenticationManager knows to use BCrypt and the custom user lookup.

28Deploying

The simplest real deployment is the same compose file on one Linux VM. The backend needs access to a Docker daemon, which rules out most serverless and managed-container platforms for the backend itself. Before exposing it to the internet:

  1. Set a long random JWT_SECRET (for example 64 bytes from openssl rand -base64 64) and keep it out of version control.
  2. Change the Postgres password.
  3. Remove the ports entries for Postgres and Redis, or bind them to 127.0.0.1.
  4. Put a TLS-terminating proxy (Caddy or nginx with Let's Encrypt) in front of port 3000, and stop publishing 8080.
  5. Fix the container leak (A4) and the output deadlock (A7). On a public site, someone will submit an infinite loop within the first day.
  6. Replace detailed 500 messages with generic ones (21.7).
  7. Back up the pgdata volume, or use a managed Postgres.
  8. Consider gVisor for the runner containers, and a dedicated VM for judging if anything else of value runs on the same host (21.9).
  9. If the frontend is hosted on a different domain (Vercel, Netlify), add that origin to the CORS configuration in SecurityConfig.

30Roadmap

The README already names the intended direction. Put together, the target architecture looks like this:

flowchart LR
  FE["Frontend (static hosting + CDN)"] --> API["API service (stateless, N instances)"]
  API --> PG[("PostgreSQL")]
  API -->|"publish job"| Q[["Queue: Kafka or Redis Streams"]]
  Q --> W1["Judge worker 1"]
  Q --> W2["Judge worker 2"]
  Q --> W3["Judge worker N"]
  W1 -->|"verdicts"| PG
  W1 -->|"ZINCRBY on first accept"| RD[("Redis: leaderboard sorted set")]
  API -->|"ZREVRANGE"| RD
  API -->|"Server-Sent Events"| FE

Figure 30.1 · Where the design is heading.

In order of value

  1. Correctness of the judge. Kill timed-out containers, stream output, enforce memory limits, report MLE, measure CPU time. Without these, nothing built on top is trustworthy.
  2. Fix problem editing. Edit test cases in place and keep historical results meaningful.
  3. A queue between API and judge. Submissions become messages; any number of judge workers consume them. This removes the in-memory executor, so restarts no longer lose work, gives back-pressure under load, and lets judging move to separate, isolated machines without the Docker socket on the API host.
  4. Push instead of poll. Server-Sent Events or WebSockets deliver status changes, including a visible RUNNING state and per-test progress.
  5. Redis leaderboard. A sorted set keyed by user, incremented on a user's first accept for a problem; reading the top 50 is one command regardless of user count.
  6. Contests. Time-boxed problem sets, per-contest rankings and penalties; this is where the Redis leaderboard pays off.
  7. Engineering hygiene. Flyway migrations, tests (service tests plus a Testcontainers judge test), CI, a .dockerignore, and specific exception handlers.
  8. Stronger isolation. gVisor or Firecracker for the runner containers, and dropped capabilities.

Each step can be shipped and measured independently. Step 3 in particular gives a concrete, measurable story: submissions per second before and after adding workers.
